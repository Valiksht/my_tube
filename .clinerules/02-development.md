
# Правила разработки проекта

Я разрабатываю проект на Windows. Хочу получать понятный,
поддерживаемый код хорошего качества. Не усложняй решения
без реальной необходимости.

## 1. Python и виртуальное окружение

Основное виртуальное окружение проекта находится в `venv`.

Все Python-команды выполняй через интерпретатор этого окружения.

Windows:
- Python: `venv/Scripts/python.exe`
- Установка пакетов: `venv/Scripts/python.exe -m pip install package`
- Запуск приложения: `venv/Scripts/python.exe -m uvicorn app.main:app --reload`
- Тесты: `venv/Scripts/python.exe -m pytest`

Ubuntu/Linux:
- Python: `venv/bin/python`

Перед запуском команд проверь наличие окружения и правильность пути.
Если окружение отсутствует или путь не совпадает с фактической
структурой проекта, остановись и сообщи мне.

Запрещено:
- Устанавливать пакеты глобально.
- Использовать глобальный pip или системный Python.
- Создавать или удалять виртуальное окружение без разрешения.
- Изменять установленный Python.

Если нужен новый пакет:
1. Объясни, зачем он нужен.
2. Проверь, нет ли подходящей установленной библиотеки.
3. Спроси разрешение на установку.
4. Установи пакет в виртуальное окружение.
5. Обнови существующий файл зависимостей.

Не создавай второй файл управления зависимостями без необходимости.

## 2. Архитектура приложения

Используй модульный монолит на FastAPI.
Не создавай микросервисы без моего согласования.

Разделяй ответственность между слоями:

- **API (Endpoints)** — маршруты, получение параметров,
  вызов зависимостей и сервисов, формирование HTTP-ответов.
  Не размещай сложную бизнес-логику и SQL-запросы.

- **Dependencies** — получение текущего пользователя,
  проверка ролей и прав, получение необходимых объектов.

- **Services** — бизнес-логика: регистрация, проверка доступа
  к видео, комментарии, подписки и другие операции.

- **CRUD** — SQL-запросы, создание, получение, обновление,
  удаление записей и загрузка связанных объектов.

- **Models** — модели SQLAlchemy, описывающие таблицы БД.

- **Schemas** — Pydantic-схемы для валидации данных
  и формирования ответов.

- **Core** — конфигурация, безопасность, общие исключения
  и общие настройки приложения.

- **Storage** — работа с объектным хранилищем.
  Не привязывай бизнес-логику напрямую к MinIO или S3.

Не дублируй SQL-запросы и бизнес-логику в разных слоях.

Перед созданием нового модуля изучи существующую структуру
и найди похожую реализацию. Не создавай дублирующие компоненты.

Если считаешь необходимым изменить архитектуру,
сначала объясни причину и предложи план.

## 3. Работа с базой данных

- Используй SQLAlchemy 2.0.
- Все операции с БД выполняй через асинхронный AsyncSession.
- Получай сессию через зависимости FastAPI.
- Не создавай отдельные подключения к БД внутри сервисов и CRUD.
- Используй Alembic для миграций.
- Не создавай таблицы вручную при запуске приложения.
- Учитывай существующие связи и ограничения БД.

## 4. Frontend и HTML-шаблоны

Для frontend используй FastAPI и Jinja2.
Не добавляй React, Vue или другие frontend-фреймворки
без моего согласования.

Используй:
- Jinja2 для HTML-шаблонов.
- HTML5 и CSS.
- JavaScript только там, где он действительно нужен.

Организация:
- Шаблоны размещай в `templates/`.
- CSS и JavaScript размещай в `static/`.
- Используй общий `base.html` и наследование шаблонов.
- Размещай HTML-страницы в отдельных роутерах или модулях.

HTML-роутеры и REST API должны использовать общие сервисы.
Не дублируй бизнес-логику и не размещай её в шаблонах.

Проверяй права пользователя на backend.
Скрытие элементов интерфейса не заменяет проверку доступа.

## 5. Качество кода

- Используй Python 3.13, если версия проекта не требует иного.
- Соблюдай PEP 8 и используй аннотации типов.
- Давай понятные имена переменным и функциям.
- Добавляй docstring для публичных функций и сложных методов.
- Не дублируй код и не создавай чрезмерно большие функции.
- Не используй глобальные переменные без необходимости.
- Предпочитай простые решения лишним абстракциям.

### Асинхронность

- Используй async/await там, где это необходимо.
- Не смешивай синхронные и асинхронные подключения к БД.
- Не выполняй блокирующие операции внутри async-обработчиков
  без необходимости.

### Обработка ошибок

Не скрывай ошибки пустыми `except`.
Не используй `except Exception` без обоснованной необходимости.

Используй подходящие HTTP-статусы:
- 400 — некорректный запрос.
- 401 — пользователь не авторизован.
- 403 — недостаточно прав.
- 404 — объект не найден.
- 409 — конфликт данных.
- 422 — ошибка валидации.

Не возвращай пользователю traceback, секреты
и внутренние технические подробности.

### Работа с файлами

- Не загружай большие видео целиком в оперативную память.
- Используй потоковую обработку и временные файлы,
  когда это необходимо.
- Удаляй временные файлы после обработки.
- Учитывай ошибки загрузки и прерывание передачи файлов.

### Тестирование

- Новая функциональность должна сопровождаться тестами.
- Исправление ошибки должно включать тест,
  подтверждающий исправление.
- Проверяй успешные сценарии, ошибки и права доступа.
- Не изменяй и не удаляй тесты только ради получения
  успешного результата.

Не переписывай работающий код, если задача этого не требует.

## 6. Работа с Git

Я хочу сохранять историю разработки проекта.
Коммиты должны отражать отдельные этапы работы.

Используй понятные сообщения:
- `feat:` — новая функциональность.
- `fix:` — исправление ошибки.
- `test:` — тесты.
- `refactor:` — изменение структуры кода.
- `docs:` — документация.
- `chore:` — настройки и служебные изменения.

Создавай небольшие осмысленные коммиты.
Не объединяй всю разработку в один большой коммит.

Без моего разрешения запрещено:
- `git reset`.
- `git rebase`.
- `git push --force`.
- `git commit --amend`.
- Удаление веток.
- Переписывание истории коммитов.

Перед коммитом:
1. Покажи изменённые файлы.
2. Проверь `git diff`.
3. Запусти необходимые тесты.
4. Объясни, что попадёт в коммит.
5. Получи моё разрешение.

Не добавляй в Git:
- Виртуальное окружение.
- `__pycache__/`.
- `.env` и другие файлы с секретами.
- Временные файлы.
- Большие видеофайлы.

Не создавай коммиты с неработающим кодом,
если это не согласованный отдельный этап.

Не изменяй чужие или несвязанные изменения
без моего разрешения.
